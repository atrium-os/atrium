# atrium-netd — pf rule lifecycle daemon

**Status:** design, 2026-05-08.
**Owner:** Atrium network policy enforcement.
**Spec dependencies:** [`portcullis.md`](portcullis.md) §0.5 (privsep architecture),
[`service-management.md`](service-management.md) §5 (decomposition rule),
[`storage.md`](storage.md) §6.1 (capability = mount; this spec is the
network-side equivalent).

The dedicated daemon that synthesizes pf rules from each jail's
manifest, applies them to `/dev/pf` as kernel anchors, and surfaces
blocked-connection events to the user. Sibling to atrium-jaild,
atrium-volumes, and the portcullisd daemons — runs in its own
narrowly-privileged jail with `/dev/pf` and read-only access to
`/etc/atrium/services.d/`.

## 1. Position

Atrium's "every app is a jail, every connection is a capability"
property requires *real* network policy enforcement, not the
"all jails on lo0 can see each other" default. atrium-netd is the
piece that translates manifest network capabilities into kernel
pf rules.

The decomposition rationale (per `service-management.md` §5):

| Daemon | Domain |
|---|---|
| atrium-jaild | privileged broker (jail_set, ifconfig) |
| atrium-volumes | volume allocation |
| atrium-portcullisd-daemon | capability mediation (RPC) |
| atrium-portcullisd-bootstrap | service supervisor |
| **atrium-netd** | **pf rule lifecycle + address allocation policy** |

Each owns one domain. Each runs in its own jail with a narrow
devfs ruleset. atrium-netd's ruleset is exactly `/dev/pf`; nothing
else holds that capability.

## 2. Architecture

```
host (init only)
└── jaild-jail (PRIVILEGED BROKER; runs atrium-jaild)
    │
    ├── atrium-netd-jail
    │     devfs: pf
    │     mount: /etc/atrium/services.d/ (ro), /var/db/atrium/jaild.state.json (ro)
    │     caps: read manifests, watch jaild state, write pf anchors,
    │           tail /dev/pflog0
    │
    ├── atrium-volumes-jail
    ├── atrium-portcullisd-daemon-jail
    ├── atrium-portcullisd-bootstrap-jail
    │
    ├── system service jails (frescod, etc.)
    └── user-app jails
```

atrium-netd is not a request-driven daemon — it doesn't accept
RPC like portcullisd-daemon. It's an **event-driven reconciler**:
watches manifests + jaild state + pflog; updates pf anchors to
match desired state; surfaces block events to atrium-notify.

This shape matches Kubernetes' kube-controller-manager or systemd's
networkd: declarative source-of-truth (manifests) → reconciliation
loop → kernel state. Reconciliation is the right shape because
network policy is a property of the system, not a per-request
authorization.

## 3. Responsibilities

### 3.1 Address space management

atrium-netd owns Atrium's reserved network ranges:

| Range | Purpose | Default |
|---|---|---|
| lo0 jail aliases | intra-host jail-to-jail communication | `127.10.0.0/16` |
| atrium0 outbound aliases | NAT'd outbound to internet | `100.64.0.0/16` |

Both are operator-overridable in `/etc/atrium/jaild.policy.toml`
(see §5.1).

The lo0 range lives in 127.0.0.0/8 (RFC 1122 reserved loopback)
and *cannot* conflict with any external network. Safe by
construction.

The atrium0 range lives in 100.64.0.0/10 (RFC 6598 carrier-grade
NAT space) and is reserved for ISP CGNAT — extremely unlikely to
appear on a home or office network. Safer default than 10.x or
192.168.x, which collide with most consumer routers.

### 3.2 Conflict detection

At startup, atrium-netd verifies the configured ranges don't
overlap with the host's existing routes:

1. Call `getifaddrs(3)` to enumerate host interfaces and addresses.
2. Read the kernel routing table via `sysctl net.route.0...`.
3. For each Atrium range (lo0 + atrium0 + any operator-configured
   alternative), check that no host route covers any of its
   addresses.
4. On conflict: log a clear error and refuse to start until the
   operator updates `/etc/atrium/jaild.policy.toml` with an
   alternative range.

Sample failure:

```
ERROR atrium-netd: configured atrium0 range 100.64.0.0/16 overlaps
host route 100.64.0.0/24 dev em1 (this host appears to be on a
CGNAT segment).

Action: edit /etc/atrium/jaild.policy.toml and set
  [network.atrium_outbound_range] = "172.31.0.0/16"
or another non-conflicting range; restart atrium-netd.
```

Conflict detection is one-shot at startup; runtime route changes
(operator adds a new VPN, etc.) are not auto-detected. Operator
intervention required.

### 3.3 pf anchor synthesis

atrium-netd reads each manifest's `[capabilities]` block (the
network-related entries) and synthesizes a pf anchor:

```pf
# anchor "atrium/jail-vscode" — auto-generated by atrium-netd
# DO NOT EDIT. Regenerated from /etc/atrium/services.d/vscode.toml

# Allow outbound NAT to internet (network.outbound = "any")
pass out from $vscode_lo0 to ! 127.10.0.0/16 nat-to (em0)
pass out from $vscode_atrium0 to ! 100.64.0.0/16 nat-to (em0)

# Allow connect to dev-* jails (network.peer_jails = ["dev-*"])
pass out proto tcp from $vscode_lo0 to 127.10.0.10 port 22  # dev-myproj
pass out proto tcp from $vscode_lo0 to 127.10.0.11 port 22  # dev-otherproj

# Default deny everything else
block in  log from any to $vscode_lo0
block in  log from any to $vscode_atrium0
block out log from $vscode_lo0 to any
block out log from $vscode_atrium0 to any
```

Each jail's anchor is independently atomic — atrium-netd uses
`pfctl -a anchor_name -f -` to atomically replace one jail's
rules without touching others. No global `pf.conf` reload.

The host's `/etc/pf.conf` references the Atrium anchor tree:

```pf
# /etc/pf.conf (operator-managed; loads at boot)
anchor "atrium/*"     # all atrium jail anchors live here
```

### 3.4 Pattern resolution

`network.peer_jails` may contain glob patterns:

```toml
[capabilities]
network.peer_jails = ["dev-*", "atrium-tools-*"]
```

When a new jail named `dev-newproj` is created, atrium-netd:

1. Notices the jail-creation event (via jaild state.json change).
2. Re-evaluates patterns in all manifests. Determines that
   vscode's `dev-*` pattern now matches dev-newproj.
3. Regenerates vscode's anchor with the new dev-newproj IP added
   to its allow-list.
4. Atomically reloads vscode's anchor.

Pattern resolution uses `fnmatch(3)`-style globs for V1; regex
support is V2 if a real use case appears. `*` and `?` only;
`[a-z]` character classes are useful but defer.

### 3.5 Block-event logging and notification

`pflog0` is FreeBSD's pflog device — every `block log` rule
writes the matched packet metadata there. atrium-netd:

1. Opens `/dev/pflog0` for reading (BPF interface).
2. Parses each block entry (uses `libpcap`-style parsing, or rolls
   its own for the BPF struct).
3. For each block: identifies which Atrium jail's anchor blocked
   it (the rule label embeds the jail name).
4. Emits an aqueduct event on a notification channel.

Future: when atrium-notify or Forum (D3) is online, the event
becomes a user-visible toast: *"vscode tried to connect to
atrium-pkg-cache:8080. Connection blocked. To allow, edit
vscode's manifest."*

For V1 (no notification UI yet), atrium-netd logs to a structured
file at `/var/log/atrium/network-blocks.log` and exposes a
sysctl ring buffer (`kern.atrium.netd.blocks_recent`) for
operator inspection.

## 4. Manifest network capability schema

The full set of `[capabilities]` keys atrium-netd interprets:

```toml
[capabilities]

# Address allocation (boolean; jaild allocates the alias)
network.lo0_alias        = true                # gets a 127.10.x.x address
network.host_alias       = true                # gets a 100.64.x.x address (atrium0); needed for outbound

# Reachability (atrium-netd writes pf rules)
network.outbound         = "any"                          # NAT out to anywhere
network.outbound         = ["github.com:443",
                            "registry.atrium.dev:443"]    # whitelisted destinations
network.inbound          = [22, 8080]                     # listen ports on this jail's IPs

# Inter-jail peering
network.peer_jails       = ["dev-*",                      # patterns matching jail names
                            "atrium-pkg-cache"]
network.peer_ports       = { "dev-*" = [22],              # port restrictions per peer
                             "atrium-pkg-cache" = [8080] }

# Specialty: full vnet (rare; for VPN clients, multi-tenant isolation)
network.vnet             = { bridge = "atrium-vnet0" }
```

Defaults: every entry not set means "no" (default-deny).
Capability prompts at install time show the full set; user
approves once.

### 4.1 Capability validation

atrium-netd does basic sanity at manifest-load time:

| Check | Failure |
|---|---|
| `peer_jails` references a name that no manifest defines AND no pattern matches | log warning, ignore that entry |
| `outbound` set without `host_alias` | refuse manifest (NAT requires the alias) |
| `inbound` ports overlap with another jail's `inbound` on the same alias type | refuse manifest |
| `inbound` listed without `lo0_alias` or `host_alias` | refuse manifest (must have somewhere to listen) |
| pattern in `peer_jails` matches own name | log warning, ignore (jail-loops are nonsense) |

Validation runs at atrium-netd startup AND when the manifest
directory changes. Failures don't crash atrium-netd; the bad
manifest is skipped, logged, and other manifests still get
their rules applied.

## 5. Configuration

### 5.1 Operator policy

`/etc/atrium/jaild.policy.toml` gains a `[network]` section:

```toml
[network]
# Jail address ranges. Defaults are usually safe; override only if
# they conflict with the host's existing networks (atrium-netd
# refuses to start in that case).
lo0_jail_range          = "127.10.0.0/16"
atrium_outbound_range   = "100.64.0.0/16"

# The cloned interface used for atrium0 aliases. atrium-netd
# ensures this exists at startup.
atrium_outbound_iface   = "atrium0"

# The host's outbound interface that NAT'd traffic uses as source.
# Auto-detected from the default route if unset.
host_outbound_iface     = "em0"

# Whether to inject a static /etc/hosts mapping for known jail
# names into each jail's mount. V1: yes; V2 maybe a tiny resolver.
inject_host_entries     = true
```

### 5.2 Boot-time interface setup

At startup atrium-netd ensures `atrium_outbound_iface` exists:

```sh
# Equivalent of what atrium-netd does (via libifconfig or similar):
ifconfig atrium0 create
ifconfig atrium0 up
ifconfig atrium0 inet 100.64.0.1/16    # gateway address for the bridge
```

If the interface already exists (atrium-netd restarting), the
command is idempotent.

### 5.3 PF state file

`/var/run/atrium/netd.state.toml` — atrium-netd's view of what
anchors are loaded:

```toml
schema_version = 1
last_sync_unix = 1715199600

[[anchor]]
jail_name      = "vscode"
loaded_at_unix = 1715199100
manifest_hash  = "sha256:abc123..."  # detect manifest changes
applied_rules  = """
pass out from 127.10.0.5 to ! 127.10.0.0/16 nat-to (em0)
...
"""

[[anchor]]
jail_name      = "dev-myproj"
...
```

Used to detect "what changed" on manifest reload and to avoid
unnecessary anchor reloads. Atomic-replaced same way jaild's
state.json is.

## 6. Event sources

atrium-netd reacts to four event sources, all on a single
kqueue:

### 6.1 Manifest directory changes

`EVFILT_VNODE` on `/etc/atrium/services.d/` for `NOTE_WRITE |
NOTE_DELETE | NOTE_RENAME`. Triggers re-read of all manifests +
re-synthesis of affected anchors.

Debounced: changes within 250ms are coalesced into a single
reconciliation pass. (Editor-save patterns often produce
write+rename+chmod within milliseconds.)

### 6.2 jaild state changes

`EVFILT_VNODE` on `/var/db/atrium/jaild.state.json`. Triggers
re-read of jail-IP mappings + pattern re-resolution.

### 6.3 pflog0 stream

`EVFILT_READ` on `/dev/pflog0`. Each readable chunk = one or more
blocked-packet records; parse and emit notifications.

### 6.4 SIGTERM / SIGINT

Graceful shutdown: log "shutting down" and exit. **Anchors are
NOT removed at shutdown** — leaving them in place means the kernel
keeps enforcing policy even when atrium-netd is restarting.

On startup atrium-netd reconciles: existing anchors are diffed
against the manifest set; mismatches are corrected. So a stale
anchor (jail removed while atrium-netd was down) gets cleaned up
on next start, not at exit.

## 7. Wire interface

atrium-netd does not expose an aqueduct RPC interface. There's no
"atrium-netd protocol class." It's purely event-driven.

Two indirect interfaces matter:

1. **Manifest dir as input.** Authoritative source of network
   policy. atrium-netd watches for changes; doesn't author.

2. **`/dev/pf` as output.** Kernel anchors are atrium-netd's
   product; userspace tools can read them via `pfctl -a "atrium/*"
   -s rules`.

Future (V2): atrium-netd may emit aqueduct events on a
notification channel for "block detected" + "anchor reloaded"
events, consumed by atrium-notify or similar UI. Out of V1 scope.

## 8. CLI

`atrium-netd-cli` for operator inspection (no daemon RPC needed —
reads pf state and atrium-netd's state file directly):

```
atrium-netd-cli list                  # show all anchors and their jail names
atrium-netd-cli show <jail>           # dump the synthesized rules for a jail
atrium-netd-cli why-blocked <jail>    # recent block events involving this jail
atrium-netd-cli reconcile             # force a re-sync (manifest → anchor)
atrium-netd-cli check-conflicts       # re-run conflict detection (returns 0 if clean)
atrium-netd-cli ranges                # show configured + actual address ranges
```

`reconcile` is the operator's escape hatch when atrium-netd's
in-memory state diverges from disk (rare; useful for debugging).

## 9. Failure modes

### 9.1 Manifest contradicts itself

A manifest declaring `network.outbound = "any"` but no
`network.host_alias` is rejected; atrium-netd logs and skips. The
jail still runs (jaild creates it as long as jaild's policy
allows), it just gets no outbound NAT rule.

The fail-shape question: should jaild refuse to launch a jail
whose manifest atrium-netd rejected? Or run it without network
policy?

V1: jaild + atrium-netd are independent; jaild launches whatever
its policy allows; atrium-netd applies whatever rules it can
synthesize. A manifest with bad network config gets a jail that
exists but can't reach anything (every connection blocks).

V2 may add a "manifest pre-check" hook in portcullisd-bootstrap
that calls atrium-netd before launch.

### 9.2 PF rule fails to load

If `pfctl -a anchor -f` fails (syntax error in synthesized rules,
kernel resource exhaustion, etc.):

- Log the error
- Keep the previous anchor in place (don't drop coverage on a
  partial reload)
- Surface a sysctl warning + a structured log entry
- Retry on next reconciliation pass

A buggy synthesizer in atrium-netd does *not* leave the system
without policy. The previous anchor stays loaded until a
successful reload replaces it.

### 9.3 atrium-netd crashes

Graceful: anchors stay loaded. Service supervisor restarts
atrium-netd. On restart it reconciles from current state.

Hung: same — anchors stay loaded; supervisor's failure-budget
mechanism eventually retires the daemon. Operator restarts
manually.

The failure mode that *would* be bad — anchors getting cleared
on atrium-netd crash — is explicitly avoided by leaving them in
the kernel.

### 9.4 pflog overrun

If atrium-netd can't drain pflog0 fast enough, the kernel drops
log entries. Block enforcement is unaffected (rules still match);
only the *notifications* are lost. Acceptable; logs include a
counter of dropped records.

## 10. Implementation order

| Stage | Goal | Estimate |
|---|---|---|
| 1 | Crate skeleton; manifest reader (reuses portcullisd's `system_services::load_dir`); state file at /var/run/atrium/netd.state.toml. | 2 days |
| 2 | Address allocation: lo0 alias range tracking + atrium0 alias range tracking; conflict detection at startup against host routes. | 3 days |
| 3 | atrium0 cloned-interface bring-up + idempotent address assignment. | 2 days |
| 4 | PF anchor synthesis (the heart): translate manifest network capabilities → pf rule text; output buffered; `pfctl -a -f -` to load. | 1 week |
| 5 | Pattern resolution (peer_jails globs); recompute when jaild state changes. | 3 days |
| 6 | kqueue event loop: manifest dir watch + jaild state watch + pflog0 reader. | 4 days |
| 7 | atrium-netd-cli operator tool. | 2 days |
| 8 | rc.d service script; integration with the existing rc.d set. | 1 day |
| 9 | End-to-end VM smoke: vscode jail can reach dev jail; can't reach a denied jail; block events surface; manifest edit reloads anchor. | 4 days |

Total: ~4 weeks focused. The pf-rule-synthesis stage (4) is the
largest piece by complexity.

## 11. Open questions

1. **pflog parsing strategy.** Use libpcap (extra dep) or
   roll our own (small but BPF struct details to track). I lean
   roll-our-own — pflog's record format is small and stable, and
   avoiding libpcap keeps the dep tree clean.

2. **Where does DNS for jail names live?** "dev-myproj" needs to
   resolve to its lo0 alias. V1 plan: atrium-netd writes
   `/etc/hosts.atrium` and bind-mounts it into each jail at
   `/etc/hosts`. V2 may want a real resolver (handles wildcards,
   updates without bind-mount churn). Punt to V2 unless real
   need emerges.

3. **Does atrium-netd-jail need to write to /etc/atrium/?**
   Atomic state file goes to /var/run/atrium/netd.state.toml. The
   /etc/hosts.atrium output (per #2) goes to /var/run/atrium/
   too. So no — atrium-netd's only write target is /var/run/atrium
   + /dev/pf. Mount /etc/atrium read-only. Cleaner privilege.

4. **IPv6 story.** The whole spec is IPv4. Real IPv6 support means
   ULA range allocation (fc00::/7), separate pf rules, etc.
   Symmetric work, separable concern. V2 unless strong demand.

5. **Multi-host policy.** Two Atrium hosts on a LAN — do they
   federate atrium-netd state? Almost certainly no for V1; each
   host is independent. Multi-host is a separate spec
   (cross-host service discovery, identity).

6. **Hot-reload of operator policy.** Today, changes to
   `[network]` in jaild.policy.toml require restarting
   atrium-netd. Could SIGHUP handle it, but range changes
   probably need full anchor regeneration anyway. V1: restart;
   V2: SIGHUP for non-disruptive reload.

7. **VPN client jails.** A jail that needs `network.vnet` (its
   own routing table) currently has minimal atrium-netd
   integration — atrium-netd doesn't synthesize anchors for vnet
   jails because they have their own pf scope. This is correct
   for V1 (vnet jails are responsible for their own internal
   policy). V2 may add cross-vnet edge rules.
