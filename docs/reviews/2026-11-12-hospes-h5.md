## 1. Fuzz targets (`hospes/fuzz`, cargo-fuzz)

- **`elf`** (from H1): `hospes-elf` over hostile ELF.
- **`proto`**: the CDM channel (`hospes-proto`). Any message that decodes must encode to the
  same bytes, and decode again to the same message. A decoded frame's planes must lie inside
  its data.
- **`codec_wire`**: the codec channel (`hospes-codec-wire`). It checks the header,
  `Picture::parse` (size bounds, plane lengths summing to the I420 size) and `split_annexb`
  (ranges in order and in bounds).
- **`vfs`**: the shim's virtual filesystem, driven by sequences of `open` / `stat` / `read`
  / `pread` / `fstat` / `close` on fuzzed paths and descriptors. Only the known virtual paths
  (and `/proc/…`) may open. A second close fails, and so does a read on a closed descriptor.
- **`install`**: `hospes-install`'s parsers, which see Google's files before and after the
  signature check. That is `.deb` → `data.tar.xz` → CDM extraction, the library check, the
  apt `Packages` / `Release` parsers, `manifest.json` and version comparison.

The `elf` and `install` runs were seeded with the committed loader fixtures (`fixtures/bin`).
No CDM or OpenH264 bytes went into any corpus, and the corpora are not committed.

The first `install` run stopped on the finding below; the others ran their hour beside it.

**The finding.** After about 10 minutes, `install` hit a panic in the `ar` crate (0.9.0,
`lib.rs:269`). A GNU name-table index in a member header (`/1519378596833500`) is used as a
slice index without a bounds check. It could only be reached after Google's signature and
hash checks, but the installer should never panic.

`hospes-install` now reads the archive itself (`ar_members`):

- It accepts only what dpkg writes: short names, an optional trailing `/`, and sizes within
  the file.
- It refuses BSD and GNU long names.
- It also caps the decompressed `data.tar` at 1 GiB, instead of unpacking a hostile `.xz`
  without bound.

The crashing input is a regression test (`tests/install.rs`,
`hostile_ar_headers_are_refused`). `install` was then rerun clean for a full hour.

## 2. Version watch

`scripts/hospes-version-watch.sh ARCH` does three things:

1. **Widevine.** It fetches Google's signed apt index and today's `google-chrome-stable`
   `.deb`. `hospes-install widevine-check` then checks the chain (pinned key, `Packages`
   hash, `.deb` hash), takes out the CDM, and checks:
   - the ELF machine;
   - the four CDM entry points;
   - that every strong import is provided by the shim.

   It installs nothing and runs nothing.
2. **OpenH264.** It fetches Cisco's binary and checks its imports
   (`hospes-install check-imports`).
3. **A decode check.** It decodes `test-assets/media/h264-baseline.mp4` with that library
   twice: under Hospes (`hospes-codec --file`) and under real glibc (`probe/h264host.c`).
   The two must be identical.

For aarch64 on an x86_64 machine, everything runs under qemu-user.

`.github/workflows/hospes-version-watch.yml` runs:

- **Daily at 06:17 UTC, on pushes to `hospes/**`, and on demand:** for both machines, the
  script, the shim against the recorded H0 import lists, and the fixture workload
  (`hospes-build.sh test-linux`).
- **Weekly (Sunday) or on demand:** each fuzz target for 5 minutes. Any crash input is kept
  as a run artifact.

First green run: run 3 (`57e5c934`). Run 4 (on demand, with fuzzing) was green in all three jobs; the fuzz job took 27 min. Today it reports:

| Machine | Chrome | CDM | CDM imports | OpenH264 2.6.0 |
|---|---|---|---|---|
| x86_64 | 157.0.8103.78 | 4.10.3112.0 | 184, all provided | 71 imports; clip identical under Hospes and glibc |
| aarch64 | 157.0.8103.78 | 4.10.3112.0 | 179, all provided | 71 imports; clip identical |

**What it does not do.** It does not run the Widevine CDM. The H4 approval covers this
cloud session only, so a behaviour check of the CDM itself (a licence and a decode)
stays manual: `scripts/hospes-h4-vm.sh`, or the Linux pieces in the H4 write-up. Moving
that into CI needs Shankar's say-so. The libraries are fetched each run and never kept.
OpenH264 comes from Cisco's plain-HTTP server; it is only parsed and run inside Hospes
and the reference harness on a throwaway runner.

**First catch.** The job's first run found that `hospes-build.sh test-linux` exited with
status 139 even when every fixture passed. `run_all` stored the fault checks' status in
the caller's `rc`. This is fixed in `57e5c934`.
