# Hospes H2: OpenH264 through the glibc shim, in the player (2026-11-11)

Step H2 of `docs/spec/hospes.md` §15: `hospes-glibc` for OpenH264's import set,
`hospes-codec`, and player integration behind the H.264 build feature. Both "done when"
conditions hold: the conformance output matches OpenH264 under real glibc on every
platform (§11.5), and the player plays an H.264 MP4 in the FreeBSD VM.

## 1. What was built

| Piece | Where | What it does |
|---|---|---|
| `hospes-glibc` | `hospes/hospes-glibc` | The glibc-ABI shim (§6), `no_std`. All 71 of OpenH264 2.6.0's imports on both machines, plus a few neighbours (`_ZdlPv`, `_ZdaPvm`, `pthread_cond_signal`). The table matches `(name, version)` exactly; baseline is `GLIBC_2.2.5` on x86_64 and `GLIBC_2.17` on aarch64, with per-machine versions where glibc differs. Anything not in the table refuses the load. |
| — memory, strings | `mem.rs` | `malloc`, `calloc`, `realloc`, `free` over the Hospes heap (`free` needs no size), `memcpy`/`memmove`/`memset`/`memcmp`, `strlen`, `strncpy`. |
| — stdio | `stdio.rs`, `printf.rs` | Our own `printf` engine over `VaList` (`%d %i %u %x %o %s %c %p %f %e %g`, flags, width, precision, length modifiers) behind `__fprintf_chk` and `__vsnprintf_chk` (which dies on overflow, as glibc's does). `fopen` fails with `EACCES`: the library has no files. `stderr` writes go to the Hospes log. |
| — threads | `pthread.rs` | Mutex, condition variable and semaphore on the glibc object layouts (state in the first `u32`), on `_umtx_op` (FreeBSD) or `futex` (Linux dev backend), with absolute-time waits. `pthread_create` runs on `hospes-rt::thread`. `sched_getaffinity` reports one CPU, so OpenH264 stays single-threaded (H0 §4). |
| — time, misc | `time.rs`, `misc.rs` | `gettimeofday`, `usleep`, `localtime` and `strftime` in UTC, `getpid`, `__errno_location`, `__stack_chk_fail`/`__stack_chk_guard`, `__cxa_finalize`, and `ceil`/`log`/`log10`/`logf`/`sqrtf` through the `libm` crate. |
| — C++ runtime | `cxx.rs` | `operator new/new[]/delete/delete[]` (abort on out-of-memory, since nothing can catch), `__cxa_guard_*`, `__cxa_pure_virtual`, and the three `__class_type_info` vtables as data objects. |
| ABI layout check | `hospes-glibc/tests/abi_layout.rs` | §11.2: the shim's glibc sizes (`pthread_mutex_t`, `pthread_cond_t`, `pthread_attr_t`, the attr types, `sem_t`, `cpu_set_t`, `timespec`, `timeval`, `struct tm`) checked for both machines. Passes. |
| `hospes-codec-wire` | `hospes/hospes-codec-wire` | The wire between the player's worker and the codec host: `kind u32, len u32, payload`. Worker → codec: DECODE (pts + one access unit), DRAIN, RESET. Codec → worker: READY, PICTURE (pts, size, packed I420), DONE, FAIL. Limits: 64 MiB per message, 16 MiB per access unit, picture size checked against the `--max` the supervisor set. `no_std` with a `std` client for the worker. |
| `hospes-codec` | `hospes/hospes-codec` | Static `no_std` binary. Opens its two fds (socket, library), calls `cap_enter`, sets the heap limit, then parses and loads OpenH264 against the shim, runs its initialisers and serves the wire. `--file LIB IN OUT` is the conformance mode (Annex-B in, I420 out), with the same order: open, `cap_enter`, load. |
| Player | `atrium-player` (feature `h264`) | The supervisor starts `hospes-codec` beside every worker, with the OpenH264 library and the worker's end of a socket pair (`ATRIUM_PLAYER_OPENH264`, `ATRIUM_PLAYER_HOSPES_CODEC`). The worker turns MP4's AVCC samples into Annex-B, puts the `avcC` SPS/PPS in front of the first access unit and after every reset, and drains the codec at end of stream. H.264 is in `supported()` only with the feature. |
| Build | `scripts/hospes-build.sh` | `codec <triple>` builds the host; `conform CODEC LIB DIR REF.sha` runs the corpus and compares hashes (works on Linux and FreeBSD). |

`libm` is the only external crate added (maths functions). Everything else is our own code.

## 2. Results

**Conformance (§11.5).** Twelve H.264 conformance bitstreams that OpenH264 supports
(Baseline, plus High without B-frames; H0 §4), decoded by `hospes-codec`, against the hash
of the same library's output under real glibc on Linux (H0's harness, single thread):

| Platform | Result |
|---|---|
| Linux x86_64 (dev backend) | 12/12 bit-identical |
| Linux arm64 (qemu-user) | 12/12 |
| FreeBSD arm64, capability mode (TCG VM) | 12/12 |
| FreeBSD amd64, capability mode (TCG VM, Nehalem CPU) | 12/12 |

Peak heap per stream is 5.6–8.2 MiB. On the longest stream (1,700 frames) Hospes took about
0.62 s against about 0.71 s for the glibc harness on the same machine; the harness also
hashes as it goes, so call it "no slower".

**Player.** `test-assets/media/h264-baseline.mp4` (160×90, 48 frames, Opus audio):

- Linux: `worker/tests/play.rs::h264_through_hospes_matches_ffmpeg` passes. Every frame
  matches ffmpeg's `framemd5`, and killing the worker mid-file restarts worker and codec
  and plays to the end. The whole player test suite passes with and without the feature.
- FreeBSD arm64 VM: `atrium-player --headless h264-baseline.mp4`, worker as an unprivileged
  user, `sandboxed true`. All 48 frame hashes equal ffmpeg's. With `--kill-worker-after 20`
  the worker restarts, the file plays to the end, and no codec process is left behind.

## 3. Decisions taken inside the spec's room

- **No unwinder for OpenH264.** §6 planned LLVM libunwind and libc++abi. OpenH264 imports
  `__gxx_personality_v0` and `_Unwind_Resume` (cleanup paths) but never `__cxa_throw`, and
  our `operator new` aborts instead of throwing. So nothing can start an unwind: those
  symbols are stubs that end the process if ever reached. The unwinder comes with H4 if the
  CDM's imports show it can throw.
- **Frames go inline over the socket.** A 1080p I420 frame is about 3 MiB per message. That
  is fine for H.264 at the sizes OpenH264 decodes well. Shared frame slots (§9) are a later
  optimisation, measured first.
- **The codec restarts with the worker, not on its own.** A crash of either ends both, and
  the supervisor's existing restart brings both back. Simpler, and the worker cannot be left
  waiting on a dead peer.
- **One thread.** `sched_getaffinity` says one CPU and the decoder is created with one
  thread, because H0 found OpenH264's threaded mode gives different output.
- **UTC only.** `localtime` is UTC: the library has no `/etc/localtime`, and OpenH264 uses
  it only for log timestamps.

## 4. Not done in H2, and where it goes

- **CanPlay.** `mime_supported` does not list `avc1` yet, so web pages will not pick H.264
  through Navigator/Limen. That needs the install route (§12: user consent, fetch Cisco's
  binary) first.
- **glibc-built loader fixtures** and the C++ exception fixture (§11.1): with the unwinder,
  in H4. OpenH264 itself now covers the glibc-built case.
- The install route (§12): fetching and verifying Cisco's binary with the user's consent.
  Today the library path comes from `ATRIUM_PLAYER_OPENH264`.
- Real-timing numbers: the VMs are TCG. Measure on the Mac (HVF) when the player work
  needs it.
