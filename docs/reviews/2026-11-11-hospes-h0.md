# Hospes H0: what OpenH264 and the Widevine CDM really use

**Date:** 2026-11-11. **Spec:** `docs/spec/hospes.md` §10 (H0). **Harness and raw data:**
`hospes/probe/` (`h0-data/`). **Machine:** cloud container, Ubuntu 24.04 x86_64, glibc 2.39.
Downloads approved by Shankar (decision 4, 2026-11-11). Nothing was disassembled: only the
dynamic symbol tables, and the libraries' behaviour under `ptrace` and `LD_AUDIT`.

## 1. Headline

1. **The CDM makes raw system calls.** Widevine's own code issues `openat`, `read`, `close`
   and `rt_sigaction` directly, not through glibc. In Hospes those would land in FreeBSD's
   syscall table with Linux numbers (Linux `read` is 0, which on FreeBSD is the indirect
   `syscall`; Linux `close` is 3, FreeBSD's `read`). **Risk R1 is real: the `SIGSYS` trap hook
   (spec §13 R1) is required for Widevine.** It is not needed for OpenH264.
2. **The CDM works in a bare host.** With no storage, no storage ID, no platform challenge and
   an honest "no output protection" answer, Widevine 4.10.3112.0 initialised, opened a session
   and produced a 1,704-byte licence request. No individualisation request on Linux desktop.
   A decrypt without a key returned `kNoKey` cleanly.
3. **Google ships an official arm64 Linux CDM.** Chrome for Linux arm64 (157.0.8103.50) carries
   `libwidevinecdm.so` for arm64, same version. No ChromeOS extraction, no patching. FreeBSD's
   4 KiB pages fit its 64 KiB segment alignment.
4. **OpenH264 is small to host,** 71 imports, 33 used, no raw syscalls, no files. **But Cisco's
   decoder only claims Constrained Baseline,** and our test confirms it: bit-exact with ffmpeg
   on Baseline and on High *without* B-frames, wrong output on Main and High *with* B-frames,
   which is what most web H.264 is. Its multi-threaded mode also gave different output from
   single-threaded. This changes the value of the OpenH264 route for the player (§6).
5. **Both need an unwinder and some C++ runtime.** Widevine imports libgcc's `_Unwind_*`;
   OpenH264 imports libstdc++'s `operator new/delete`, `__cxa_guard_*`, the type-info vtables
   and `__gxx_personality_v0`. Hospes needs a freestanding LLVM libunwind and the libc++abi
   pieces (both Apache-2.0 with LLVM exception).

## 3. Widevine: what it did (x86_64)

Run: `cdmhost` (Initialize, CreateSessionAndGenerateRequest with a Widevine PSSH, one
no-key Decrypt, Destroy), under the tracer and the audit module.

**Imports actually called:** 49 of 184 (`h0-data/wv-x64.calls`). By volume: `memset`
(110 k), `memcmp`, mutexes and conds, `madvise` (90), `memcpy`, `mprotect` (63), `syscall`
(27), `__tls_get_addr`, `uselocale`, `mmap64`, `prctl`, `__cxa_atexit`, `pthread_once`,
`getpid`, `__register_atfork`, `clock_gettime`, `__xstat64`, `uname`, `sysconf`,
`setpriority`, one `pthread_create`, `open64`, `getenv`, `sscanf`. **It imports no `malloc`**:
it has its own allocator over `mmap64`/`madvise`/`mprotect`.

**Through `syscall()`:** `gettid` ×15 and `getrandom` ×10. **`getenv`:** `OPENSSL_ia32cap`.
**`sysconf`:** page size. **`prctl`:** `PR_SET_VMA` (naming anonymous mappings) ×7.

**Raw syscalls from the CDM's own text** (caller address inside `libwidevinecdm.so`):

| Linux syscall | Count | What for (from arguments) |
|---|---|---|
| `openat` (257) | 14 | `/proc/self/maps` ×9, `/proc/net/unix` ×5 |
| `read` (0) | 44 | reading those |
| `close` (3) | 14 | |
| `rt_sigaction` (13) | 4 | **queries only** (no new handler) for `SIGILL`, `SIGTRAP`, `SIGABRT`, `SIGSYS` |

**Files through imports:** `/dev/urandom` (`open64`), and `stat` of
`/sys/fs/cgroup/cpuset/chrome` and `/sys/fs/cgroup/schedtune/chrome` (Chrome's thread-priority
cgroups; absent here, which it tolerates).

**No** executable `mprotect`/`mmap` from the CDM (no run-time code generation on this path),
no sockets, no `fork`/`exec`, no `ptrace`, no reads of `/proc/self/status`.

**Host callbacks used:** `QueryOutputProtectionStatus` once during Initialize (we answered
"succeeded, no links, no protection"); `OnInitialized(true)`; `OnResolveNewSessionPromise`;
`OnSessionMessage(kLicenseRequest, 1704 bytes)`. **Not used** on this path: `CreateFileIO`,
`RequestStorageId`, `SendPlatformChallenge`, `SetTimer`. `VerifyCdmHost_0` was never called
and was not needed.

## 4. OpenH264: what it did (x86_64)

Run: `h264host`, a 1280×720 x264 stream, single- and four-thread decoder.

- **Imports called:** 33 of 71 (`h0-data/oh264-x64-t4.calls`): `memset`, mutex/cond,
  `sem_*`, `gettimeofday`, `malloc`/`free`, `memcpy`/`memmove`, `__vsnprintf_chk` (logging),
  `operator new/delete`, `pthread_create/join` and attrs (threaded mode), `sched_getaffinity`.
- **No raw syscalls, no files, no signals, no executable mappings.**
- **Correctness against ffmpeg:**

| Stream | OpenH264, 1 thread | 4 threads |
|---|---|---|
| Constrained Baseline 640×360 | bit-exact | differs |
| High, no B-frames 1280×720 | bit-exact | — |
| Main, with B-frames | differs | — |
| High, with B-frames | differs from frame 3 on | differs |

With `DecodeFrameNoDelay` (Cisco's console default). `DecodeFrame2` refused these streams
(`PrefetchPic ERROR`). Cisco's README claims only Constrained Baseline for the decoder, so
this is expected, not a harness fault we know of.

## 5. arm64

Static data only (the container is x86_64): import sets match x86_64 except architecture
helpers (`__stack_chk_guard` and `__ctype_b_loc` instead of `__tls_get_addr`, a few math
functions), and the CDM uses `TLSDESC` and `IRELATIVE`. A dynamic run on arm64 Linux (a
Linux VM on the Mac) is still to do before H4 on arm64.

## 6. What changes in the plan

1. **K1, the `SIGSYS` trap hook, becomes a required step before H4** (Widevine). Its handler
   needs Linux `openat`/`read`/`close`/`rt_sigaction` at least; the virtual filesystem serves
   the opens. Spec §13 R1 and §15 updated.
2. **Virtual filesystem** adds `/proc/net/unix` (header line only, no sockets) and
   `/dev/urandom`; `/proc/self/maps` must be right because it is read nine times.
3. **Signal queries.** `rt_sigaction` queries for `SIGSYS` will see Hospes's trap handler.
   Firefox's seccomp sandbox also installs a `SIGSYS` handler and Widevine runs there, so we
   answer truthfully.
4. **Shim scope (spec §6.2):** add libgcc unwinder entry points, libc++abi pieces
   (`__cxa_guard_*`, `__cxa_pure_virtual`, type-info vtables as data objects,
   `__gxx_personality_v0`, `operator new/delete`), old stat ABI (`__xstat64`, `__fxstat64`),
   `_l` locale functions with the C locale, `catopen`/`catgets` stubs, `sem_*`,
   `__register_atfork`, `setpriority`/`sched_setscheduler` (accept, do nothing), `syscall()`
   for `gettid` and `getrandom`.
5. **OpenH264 runs single-threaded** in Hospes (spec §9 already said one thread per instance).
6. **OpenH264 covers less H.264 than assumed.** Most web H.264 is Main or High with B-frames,
   which Cisco's decoder does not handle correctly in our test. So OpenH264 through Hospes
   gives WebRTC-style and Baseline content, not general playback. The player's §9.3 H.264
   decision should weigh that: the alternatives are a licensed decoder of our own (with a Via
   LA licence) or hardware decode, which is parked. Firefox uses OpenH264 for WebRTC and
   system or ffmpeg decoders for playback; our earlier note that it uses OpenH264 for
   playback was too broad.
7. **H2 still comes first** as the loader's proving ground (it needs no hook), but its product
   value is now WebRTC/Baseline H.264, so H3/H4 (the CDM) carry the main value.
