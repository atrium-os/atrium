# Hospes H3: Clear Key through the CDM host, in the player (2026-11-12)

Step H3 of `docs/spec/hospes.md` §15: `hospes-proto`, `hospes-cdm` with a test CDM, CENC and
CBCS sample information from the demuxers, the control and data channels, and the
per-origin store. Both "done when" conditions hold:

- Clear Key content plays through Hospes: three encrypted clips (cenc fragmented MP4, cbcs
  MP4, encrypted WebM) play in the player on Linux and in the FreeBSD arm64 and amd64 VMs,
  and every frame equals the clear source's.
- Outputs equal the Linux reference host's: the 47-line transcript of the test CDM's
  scenario under `hospes-cdm` is identical to the reference host's on Linux x86_64, Linux
  arm64 (qemu-user), FreeBSD arm64 and FreeBSD amd64.

Commits: `5de82b6` (host, protocol, test CDM), `41f1666` (demuxers), `9b36af0` (player),
and this write-up's commit (VM script, docs).

## 1. What was built

| Piece | Where | What it does |
|---|---|---|
| `hospes-proto` | `hospes/hospes-proto` | Messages on both channels, `kind u32, len u32, payload`. Control (supervisor ↔ CDM): Init, policy, certificate, create/load/update/close/remove session; Ready, Initialized, promise results, session messages, key changes, expiration, closed, Fail. Data (worker ↔ CDM): Decrypt, InitAudio/InitVideo, DecryptAndDecode, Reset/Deinit; Decrypted, InitResult, Decoded, Done. Limits: 64 MiB per message, 4096 list items, 1 KiB short fields; `Frame::planes` checks a decoded frame's geometry against the buffer and a maximum size. `no_std`, with blocking `std` send/receive. |
| `hospes-cdm` | `hospes/hospes-cdm` | Static `no_std` binary, like `hospes-codec`. Takes its fds (control, data, library, store), calls `cap_enter`, sets the heap limit, loads the CDM against the glibc shim, calls `InitializeCdmModule_4` and `CreateCdmInstance(10)`, then serves both channels from one `poll` loop with timers and deferred callbacks. |
| — C++ ABI | `abi.rs`, `host.rs` | `ContentDecryptionModule_10` called through its vtable; `Host_10`, `Buffer`, `DecryptedBlock`, `VideoFrame` and `FileIO` built in Rust as `repr(C)` objects with Itanium vtables (offset-to-top, RTTI slot, two destructor slots). Struct layouts are checked against the header's `CHECK_TYPE` sizes. |
| — host callbacks | `host.rs` | Promise results, session messages, key changes, expiration and close go to the control channel. `SendPlatformChallenge` answers "not supported"; output protection reports the link mask the supervisor gave and no protection (§8.2). `RequestStorageId` returns the origin's random id. |
| — store | `store.rs` | `FileIO` over the store directory fd (§8.4): record `NAME` (`[A-Za-z0-9._-]{1,64}`) is `r-NAME`, written as `w-NAME` and renamed over it; zero bytes deletes; an `index` file keeps sizes so the 1 MiB / 64-record caps need no directory listing; `storage-id` holds 32 random bytes. |
| Test CDM | `hospes/test-cdm` | A Clear Key CDM in C++ compiled against the real `content_decryption_module.h`: `cenc`, `cbcs` with patterns, `cenc`/`keyids`/`webm` init data, temporary and persistent sessions (persistent ones stored through `FileIO`), the storage id, timers, and a test decoder for the decrypt-and-decode path. No STL, its own AES; only the four entry points are exported. `refhost.cc` is a reference host on real glibc; both hosts run the same scenario (`scenario.h`) on vectors from `make-vectors.py`, whose AES output is checked against Python's `cryptography`. Built `.so` files and vectors are committed. |
| `hospes-cdm-check` | `hospes/hospes-cdm-check` | Plays the supervisor and the worker against `hospes-cdm` and prints the same transcript as the reference host, so the comparison covers the protocol as well as the host. |
| Demuxers | `atrium-player/demux` | MP4: `schm`/`tenc` in `sinf`; per-sample IVs and subsamples from `senc`, or from `saiz`/`saio` (file offsets in plain files, relative to the fragment's base in fragments); constant IVs; `pssh` boxes as init data. WebM: `ContentEncryption` with AES-CTR, the signal byte, IV and partitions turned into subsamples, the key id as init data. Each `Sample` carries its `Crypto`; the demuxer emits `Event::InitData`. |
| Player | `atrium-player` | With a CDM configured, the supervisor starts `hospes-cdm` beside each worker: the control channel is the supervisor's, the data channel the worker's. The worker sends init data up (new `InitData` records); the supervisor opens a session, answers the Clear Key licence request and tells the worker when keys are usable (`KeysChanged`). The worker decrypts each sample through the CDM just before decoding and waits on `NO_KEY`. |
| Test media | `test-assets/media/clearkey`, `scripts/media-encrypted-clips.sh`, `scripts/webm-encrypt.py` | The three clips, made with GPAC and our WebM encryptor from existing clear clips, so the clear clips' frame hashes are the reference. Key id `00112233445566778899aabbccddeeff`, test-only key. |
| VM run | `scripts/hospes-h3-vm.sh`, `hospes/test-cdm/vm/run.sh` | Cross-builds everything for the guest, copies it in and runs the transcript check and the player runs as `nobody`. |

## 2. Results

**Transcript (§11.3).** `hospes-cdm-check` against the committed reference transcript (47
lines: initialisation, sessions from `cenc` and `keyids` init data, licence updates, key
statuses, policy and server-certificate answers, cenc and cbcs decrypts including pattern
and partial-block cases, no-key and decrypt-error results, decoder initialisation and
decrypt-and-decode frames with their geometry, a persistent session saved, closed and loaded
again through `FileIO`, and the storage id's length in the licence request):

| Platform | Result |
|---|---|
| Linux x86_64 | identical |
| Linux arm64 (qemu-user) | identical |
| FreeBSD arm64, capability mode (TCG VM) | identical |
| FreeBSD amd64, capability mode (TCG VM) | identical |

**Demuxers.** New tests decrypt each clip with the sample information the demuxer gives
(an AES in the test, checked on the FIPS-197 vector) and compare with the clear source's
samples: all three are byte-for-byte equal, read in one piece and in 7-byte and 4 KiB
chunks. The WebM clip covers partitioned, whole-frame and clear frames.

**Player.** Each clip, 48 frames at 160×90 with Opus audio:

- Linux: `worker/tests/play.rs` plays all three with every frame's hash equal to the clear
  source's (ffmpeg's `framemd5` of the layer); the MSE path in 7000-byte appends gives the
  same; killing the worker, or killing only the CDM host, restarts both and loses or repeats
  no frame; keys that don't include the media's key give an error in under 3 s (the test's
  limit), not a watchdog timeout; without a CDM, encrypted tracks are refused and the decoders
  never see ciphertext. The whole suite ran clean 8 times in a row, and 3 more after the
  CDM-kill test was added.
- FreeBSD arm64 and amd64 VMs: `atrium-player --headless` as `nobody`, worker sandboxed, for
  each clip with and without `--kill-worker-after 20`: all 48 frames equal the clear source's
  every time, one restart where asked, and no `hospes-cdm` left afterwards.

## 3. Decisions taken inside the spec's room

- **The player uses decrypt-only.** H0b showed Widevine needs decrypt-and-decode for video.
  `hospes-cdm` and the protocol carry that path and the transcript tests it, but the test CDM's
  decoder is a stub that refuses real codecs, so the player's use of it waits for H4, where
  the real CDM is there to test against. Audio stays decrypt-only either way.
- **The CDM lives and dies with its worker.** One `hospes-cdm` per worker, killed with it. A
  restarted worker reads the file again, reports its init data again, and the new CDM gets a
  new temporary session. A CDM that exits counts as a crashed worker (both are replaced, once
  per playback as before). A refused licence, or media we have no key for, is an error at
  once (`UNSUPPORTED`).
- **The supervisor stands in for the page.** In a browser, EME code on the page fetches the
  licence. The standalone player has no page, so the supervisor answers Clear Key requests
  from keys it was given (`ATRIUM_PLAYER_CLEARKEY=KID:KEY,...`). A licence server reached
  through Nuntius comes with H4. The control channel is what Navigator's EME will drive.
- **Samples go inline over the data socket.** Like H2's frames: simple, and fine at these
  sizes. Shared slots for `Allocate` (§8.2) come when Widevine's 1080p frames make the copy
  show up in measurements.
- **8-byte IVs are padded to 16** by the worker, as Chromium's parser does, so the CDM only
  ever sees 16-byte IVs.
- **One thread in `hospes-cdm`.** The Chromium interface lets the host call the CDM from one
  thread; the CDM's own threads (if Widevine has any) are H4's question.

## 4. Not done in H3, and where it goes

- **The store directory isn't rights-limited yet.** `hospes-cdm` is in capability mode, but
  the store fd the supervisor passes still has full rights, and the player passes none unless
  `ATRIUM_PLAYER_CDM_STORE` is set (no persistent licences, so none is needed for Clear Key
  playback). `cap_rights_limit` on it, and the store's place on a Tessera volume keyed by
  origin, come with H4.
- **No jail or separate user for the CDM.** It runs as the player's user in capability mode.
  The one-shot jail and own user (§3) come with H4, before the real CDM runs.
- **Encrypted H.264** would now go to `hospes-codec` after decryption, but no clip tests it.
  H4's Widevine streams are H.264 and use decrypt-and-decode anyway.
- **Refused for now:** `seig` key rotation (MP4 sample groups), the `cens` and `cbc1`
  schemes, laced encrypted WebM blocks, and `saio` offsets pointing outside `moov`/`moof`.
  Each refusal is an `Unsupported` error, never a wrong decrypt.
- Real-timing numbers: the VMs are TCG.
