## 0. What the first real run found

The real CDM failed four ways before it played; each is fixed:

1. **`syscall(SYS_futex)` was ENOSYS**, and the CDM's allocator (PartitionAlloc) treats a
   failed lock wait as fatal: a `CHECK` (`int3`) on the first contended lock. The shim's
   `syscall()` now does `FUTEX_WAIT`/`FUTEX_WAKE` and their bitset forms with a full mask,
   on the runtime's `_umtx_op` / `futex` waits. Found by tracing system calls only.
2. **hospes-cdm was created for `org.w3.clearkey`.** The player now passes the key system
   (`com.widevine.alpha` for `libwidevinecdm.so`; `ATRIUM_PLAYER_KEY_SYSTEM` overrides).
3. **A clear lead.** Shaka Packager writes two sample entries (`encv`, then `avc1`) and the
   first fragments use the clear one, with no CENC aux information. The MP4 demuxer refused
   them; it now treats a fragment whose sample description is not `encv`/`enca` as clear.
4. **A licence request from a bare key id.** The audio WebM carries only a key id; Shaka's
   proxy answers 500 to a request made from one (its player uses the manifest's PSSH for
   every track). The player now holds key-id init data while another licence is under way,
   drops it if that licence made its key usable, and does not fail playback when a key-id
   session's licence is refused beside other sessions.

The VP9 WebM representation is not checked: it carries only key ids, and this check reads
no manifest. Nothing here ran the CDM outside Hospes, and nothing was disassembled.

## 1. H4a: the shim against the real import list

`hospes-glibc/tests/imports.rs` reads the import lists recorded in H0
(`probe/h0-data/wv-*.so.imports`, `libopenh264-*.imports`) and checks every strong
`(name, version)` against the shim's table, which matches name and version exactly. The
pending list is empty. New in the shim: pthread attributes, condition-variable clocks,
rwlocks, `pthread_once`, keys with destructors, thread names and affinity; `setjmp` /
`longjmp` (assembly, both architectures); `gmtime_r`, `localtime_r`, `timegm`, `mktime`,
`strftime_l`; `__isoc99_sscanf`; a handful of maths functions; `aligned_alloc`,
`__vfprintf_chk`, `__getauxval`; and both the old symbol versions and glibc 2.34's
(`pthread_*`, `sem_*`).

## 2. H4b: exceptions

Widevine links libc++abi statically and imports only libgcc_s's `_Unwind_*` ABI. The shim
provides it with the `unwinding` crate (0.2.11, vendored in `hospes/vendor/unwinding`):

- **Finding frames.** A table of up to 8 loaded libraries' `.eh_frame_hdr`, plus our own
  executable's (found from `AT_PHDR`), since the unwinder starts in our
  `_Unwind_RaiseException`. Executables are built with `-C force-unwind-tables=yes`.
- **Two AArch64 fixes to the crate** (offered upstream later): gimli must be told the
  vendor is AArch64 for every FDE finder, or `DW_CFA_AARCH64_negate_ra_state` (0x2d) fails
  to parse; and the return address is stripped of its pointer-authentication bits
  (`xpaclri`) with register 34 (RA_SIGN_STATE) skipped.
- **The fixture**, `fixtures/src/glibc.cc`: a C++ library shaped like Widevine (LLVM
  libc++abi static, old glibc symbol versions via `.symver`), checking exceptions (1–8),
  threads (10–19), text (30–37) and process calls (40–45; `mprotect` with `PROT_EXEC` must
  fail with `EACCES` under Hospes). It passes under Hospes and, as a reference, under real
  glibc through `dlopen`, on Linux x86_64 and arm64 (qemu), and in both FreeBSD VMs with
  the K1 trap on.

## 3. The licence route

- **Nuntius POST** (`docs/spec/nuntius.md` §3.1): `Open.body` carries a content type and
  at most 32 KiB. A POST is never retried and never follows a redirect (refused as policy),
  and takes no range.
- **The player** (`atrium-player/player/src/cdm.rs`): with `ATRIUM_PLAYER_LICENCE_URL`,
  each licence request and renewal (message types 0 and 1) is POSTed as is through the
  system fetcher, on its own thread. A 2xx answer of at most 1 MiB within 30 s goes back to
  the CDM as `UpdateSession`. Tested end to end with Clear Key through a stand-in fetcher.

## 4. The install route: `hospes-install`

The system fetches three files and `hospes-install widevine-deb` checks the chain:

1. `InRelease`'s clear signature against Google's Linux signing key, pinned by fingerprint
   (`EB4C 1BFD 4F04 2F6D DDCC EC91 7721 F63B D38B 4796`);
2. the SHA-256 of `Packages` as `InRelease` lists it;
3. the `google-chrome-stable` entry's size and SHA-256 against the `.deb`.

It then unpacks `ar` → `data.tar.xz` → the CDM and its `manifest.json` (pure Rust:
`lzma-rs`, `tar`), and checks the library without running it: the ELF machine, the four
CDM entry points, and every strong import provided by the shim. It installs read-only into
`DEST/<version>/` with a `current` link, and refuses a downgrade. `widevine-file` does the
same for a user's own library. Against today's package: "CDM 4.10.3112.0: 184 imports, all
provided".

## 5. Video through decrypt-and-decode

H0b found Widevine refuses decrypt-only for part of every video stream, so an encrypted
video track goes to the CDM whole (`atrium-player/worker/src/cdmvideo.rs`) when the CDM
accepts `InitVideo`:

- **H.264** goes in as Chrome sends it: Annex-B (4-byte length fields become start codes in
  place, so the subsample map is unchanged), SPS and PPS before every key frame (added to
  the first clear run), and no extra data. Profiles from `avcC`. Other length sizes stay on
  decrypt-only.
- **VP9** profile 0 as stored.
- Frames come back as I420 and are bounds-checked (`Frame::planes`) before a plane is used.
  `NO_KEY` waits for keys as decrypt-only does. Seeks reset the decoder; the end drains it
  with empty samples.
- A CDM that refuses (the Clear Key test CDM accepts only its own test decoder) leaves the
  track on decrypt-only and our decoders, so every H3 clip still plays.

Also fixed: `clear_key_survives_a_cdm_crash` failed about 1 run in 4 (before this work as
well). When the CDM was killed, the worker's error could reach the supervisor before the
CDM's exit did. A worker error now counts as a restart when its CDM has exited.

## 6. The VM check: `scripts/hospes-h4-vm.sh`

The container has no route out, so the guest gets a fixture address (as
`nuntius-vm-check.sh` does): `cwip-shaka-proxy.appspot.com` maps to 1.2.3.100, whose port
443 is a host-side relay. The relay holds a throwaway CA's certificate for that name and
forwards each POST to the real proxy through this environment's HTTPS proxy. The guest
trusts the throwaway CA. Then, in the guest (`hospes/vm/h4-run.sh`):

1. `hospes-install widevine-deb` installs the CDM from Google's files.
2. `nuntius/examples/fetcher-standin` stands in for portcullisd's `OpenFetcher` (the player
   runs outside an app jail here, as in H3) and starts the real `nuntiusd` as uid 65023.
3. The player plays `v-0144p-0100k-libx264.mp4` with
   `a-eng-0096k-libopus-2c.webm` as `nobody`. Pass: ended, at least 1,490 frames, the last
   at 59 s or later, at least 2.8 M audio frames, worker sandboxed.

`INSTALL_ONLY=1` stops after step 1, before anything runs the CDM. The same pieces run on
Linux for quick checks (`nuntiusd --unconfined-for-testing` through the stand-in, the relay
on 127.0.0.1:443).

## 8. Follow-up: the stream in the arm64 VM (2026-11-12)

`SRC=… ARCH=aarch64 sh scripts/hospes-h4-vm.sh` in the FreeBSD arm64 VM (fork kernel,
`hospes_trap.ko`). `hospes-install` installs Widevine 4.10.3112.0 from Google's arm64 Chrome
157.0.8103.78 package, and angel-one plays as `nobody`: 1,500 frames (1,473 distinct, the last
at 59.96 s), 2,880,648 audio frames, worker sandboxed, no `hospes-cdm` left, 18 s. The relay
saw the same two POSTs as on amd64: the licence (200) and the refused bare key-id request
(500, tolerated as in §0).

No arm64-specific change to Hospes was needed. Two harness fixes:

- **The host's index step** verified Google's index for the host's own architecture, so an
  arm64 run on an x86_64 host stopped there. `hospes-install widevine-index` takes an optional
  `amd64|arm64`, used only to name the package to fetch; the guest still verifies the whole
  chain for its own architecture. The script also stops cleanly when the step fails.
- **The kernel copy** (`hospes-k1-vm.sh kernel`) hashed the tarball as it was written, so a
  file cut short by a full disk was sent and only caught in the guest. It now writes the
  tarball, then hashes the file.
